## Assessment

The source contains substantial reusable engineering. Preserve the single Narrative GAS damage resolver, Hound and Handler activation epochs and attack-token leases, finite projectile lifetimes/reflection cap, weak-point effect/count ownership, permanent sever masks, and mission-scoped corruption permissions. This is not a feature-empty prototype. However, several synchronous callback boundaries still violate the same ownership and transaction invariants already protected elsewhere. The strongest findings below are source-proven execution paths, with engine regressions still required. They are not claims that a specific unseen map has already failed.

## ED-01: nested damage can overwrite another committed hit and corrupt fatal results

**Priority P1, high confidence; central gameplay/data-integrity defect.**

- **Exists:** `N/Private/GAS/NarrativeAttributeSetBase.cpp` clears incoming meta attributes before callbacks (224–227), captures OldShield/OldHealth/OldPoise (541–543), computes routed resource damage (545–599), then writes Shield, Health and Poise (622–654). Typed results and death ordering are unified.
- **Required:** TDD §6.3 ordered shield/health/poise/death resolution and reliable combat telemetry; §6.7 safe interactions between effects. One hit must not erase another accepted hit, and one death must have one authoritative outcome.
- **Failure:** `SetShield` (624) can run ordinary GAS attribute listeners synchronously. Explicit `OnShieldBroken` and `Event_Shield_Broken` also execute at 631–636 before `SetHealth(OldHealth - AppliedHealthDamage)` at 641. A nested attack changes Health, but the outer transaction subsequently overwrites that change using its stale Health snapshot. `SetHealth` and `SetPoise` have equivalent callback exposure. `bFatal` is sampled at 658, before Poise and status event callbacks at 660–696, allowing later reentry to invalidate the still-pending death/result assumptions. There is no per-target transaction serialization in this resolver.
- **Reproduction:** target Shield=10, Health=100; apply outer body damage=20. A one-shot Shield change/break listener applies nested body damage=30 after shield reaches zero. Nested resolver takes Health to70, then outer writes90. Expected total Health is60, observed source path gives90. A lethal nested hit is more dangerous: a zero-Health/dead target may be rewritten above zero by the outer write, while the ASC's death state and telemetry still reflect a kill. No race or network client is needed.
- **Decision:** refactor the existing resolver transaction boundary. Preserve its routing math and typed receipts. Serialize nested combat requests for the same target until the outer mutation and its terminal outcome are committed, or use an equally explicit staged transaction scheme. A callback-safe bounded queue needs a policy for recursive thorns/status loops, owner/avatar replacement and target destruction. Do not merely move explicit break broadcasts: GAS attribute delegates inside the setters also reenter.
- **Dependencies/risk:** high change risk because Echo, Shield delay, weak-point break, dismemberment, sustain drops, statuses and death all consume the result. Death explosions legitimately damage other actors, so do not apply a global combat lock or discard every reentrant hit. Snapshot callers also need to observe committed state rather than an intermediate resource tuple.
- **Order:** first gameplay hardening slice, before accepting further resource/death fixes as reliable.
- **Regression:** real GAS effects in a transient world, not a duplicated arithmetic policy. Nested damage from Shield attribute change, explicit Shield break, Health change, Poise break and status callback; nested healing; fatal nested attack; source/target destruction; recursion cap. Verify final resources, exact accepted damage sums, one terminal transition and per-transaction receipts. Existing `SovCombatRoutingRuntimeTests.cpp` tests pure Poise/control, defenses and weak-point reset reentry, not nested resolver mutation.

## ED-02: a pickup grants resources before reserving itself

**Priority P1, high confidence; repeatable resource duplication through legitimate callbacks.**

- **Exists:** `P/Private/Combat/Pickups/SovCombatSustainPickup.cpp:144–177` checks `bClaimed`, validates player, calls `TryGrantTo`, then sets `bClaimed=true` at172. Ammo supports partial accepted packs (`SovAmmoCombatSustainPickup.cpp:44–78`). Echo refuses a full meter and correctly avoids inactivity refresh in that case (`SovEchoCombatSustainPickup.cpp:33–44`).
- **Required:** approved narrow sustain exception and authoritative, consume-once resource economy; partial ammo acceptance must conserve pack contents.
- **Failure:** resource callbacks execute before the claim. Echo `TryGrantTo` calls `AddEcho` at41; `SovEchoComponent.cpp:236–240` invokes attribute and grant listeners synchronously. Reentering overlap during one such listener sees an unclaimed mote and grants it again. Ammo calls `TryAddItemFromClass` at61 and subtracts `AmmoQuantity` only at73; an inventory listener can reenter while the original quantity remains available. The outer subtraction may then make the pack quantity negative after the inner call consumed it.
- **Reproduction:** use a native fixture exposing the protected overlap path; on first `OnEchoGranted`, invoke that same pickup's overlap again. Echo0, mote10, Max100 yields20 for one mote. For ammo10 and reserve capacity>=20, one inventory-added callback invokes overlap again; reserve gets20 and the two subsequent quantity subtractions produce a negative remainder. A real-world equivalent is an overlap refresh or movement caused by resource listeners.
- **Decision:** extend the existing pickup with an in-progress reservation before calling any resource mutation. Clear the reservation on failure/partial acceptance; finalize claim once on full consumption. Keep a separate partial-pack remaining quantity and stage/commit it safely around inventory callbacks. A global resource lock is unnecessary.
- **Dependencies/risk:** medium; inventory delegates, Echo meter delegates, destruction/encounter cleanup during collection and partial ammo behavior. Preserve the existing single-stack reserve cap and full-meter rejection.
- **Order:** same first transaction slice or immediately after ED-01.
- **Regression:** real pickup overlap and actual inventory/Echo delegates; nested overlap, partial pack, full meter/reserve, player death/avatar replacement and pickup destruction inside grant callback; assert resources never exceed original pack entitlement and exactly one collection presentation. No dedicated native sustain collection regression was found; foundation tests inspect CDO composition only.

## ED-03: Selene Deflection can continue starting after it has already been cancelled

**Priority P1, high confidence; defense/action lifecycle defect.**

- **Exists:** `P/Private/Abilities/SovGameplayAbility_SeleneDeflection.cpp` grants local-predicted defense, cancellation-tag listeners and finite recovery. Guard has already been hardened with component ownership epochs and reentry regression tests; Deflection retains an older ordering.
- **Failure A:** ability `ActivateAbility` calls `DeflectionComponent->BeginDeflection()` at130–131. Component adds the defense tag and broadcasts `OnDeflectionStarted` at `SovDeflectionComponent.cpp:136–154`. A listener cancels the ability. `EndAbility` at186–189 skips component cleanup because `bDeflectionStarted` is not set until control returns to outer Activate at137. Outer Activate then continues binding cancellation delegates, committing costs/cooldown, starting weapon montage, invoking the start hook and creating a WaitDelay task (138–161), with no `IsActive` or activation-generation recheck. The ended action can retain a live defensive window until its timer and leave post-end task/listener work.
- **Failure B:** component `SetOwnedLooseTag` changes the GAS tag before changing its owned flag (249–274). A `State_Deflecting` NewOrRemoved callback that calls EndDeflection during Add sees `bAppliedDeflectingTag=false`, so its removal is skipped. This mirrors an already-covered Guard regression (`SovGuardRuntimeTests.cpp:159–187`) but is not hardened here.
- **Required:** precise defense timings and deterministic cancellation across death, ragdoll, cinematic takeover and ordinary authored callbacks. Cancellation must retire all gameplay state before any continuation.
- **Decision:** refactor Deflection to the established Guard-style ownership discipline, preserving its distinct resource/reward semantics. Claim startup before external callbacks, add activation epochs, recheck actor/ASC/identity after every callback/commit/montage boundary, make EndAbility idempotent and honor valid/scope-locked GAS ending. Set owned tag state before emitting tag callbacks and verify continuation ownership afterward. Direct Blueprint component entry should share the same interruption cleanup contract as GAS entry.
- **Dependencies/risk:** medium to high: predicted client window vs authoritative consumption, perfect-deflection event/Echo award, weapon montage ownership, shared PlayerState ASC and console input cancellation. Do not replace the narrow Deflection policy with sustained Guard.
- **Order:** first action lifecycle hardening slice after the central damage boundary.
- **Regression:** native OnDeflectionStarted callback cancels, cancels-and-reactivates, or switches avatar; tag-add callback ends component; start Blueprint hook cancels; repeat End does not remove replacement state. Confirm zero retired tags/timers/listeners/costs and exactly one valid defense reward. Existing test suite has defense routing with tags, not these real Deflection activation boundaries.

## ED-04: boss/elite finisher phase can be durably consumed without delivering its outcome

**Priority P1, high confidence for lost outcome; authored boss progression blockage is conditional.**

- **Exists:** finite 0.8–1.8s aligned finishers, 0.35s noncinematic fallback, target reservation, nav/LOS/exit checks, nonlethal elite/boss damage and owned protection effects. `USovFinisherTargetComponent` persists resolved phase tags.
- **Failure:** `P/Private/Abilities/SovGameplayAbility_Finisher.cpp:211` calls `CommitPhase` before applying damage at213. The target component immediately adds the phase to `ResolvedPhases` (`P/Private/Combat/SovFinisherTargetComponent.cpp:60–63`), which is `UPROPERTY(SaveGame)` (`Public/Combat/SovFinisherTargetComponent.h:42`). If a damage/Health callback cancels the player action or starts a cinematic, the `OwnsAction` check at214 returns before the only `Event_Finisher_PhaseResolved` producer at217–219. That phase is permanently unavailable for repeat finisher (`TargetComponent.cpp:35–37`); Load only clears transient reservation, with no outcome reconciliation. The public `HasResolvedPhase` getter allows a bespoke BP workaround but no native consumer/recovery mechanism exists.
- **Reproduction:** aligned eligible elite/boss with RequiredPhaseTag active; on first applied Health change cancel the finisher handle. The target's phase is saved as resolved, the event is never sent, and another attempt is refused. Save/reload preserves refusal. A boss graph awaiting the advertised event stalls; a graph already consuming the Health threshold may happen to progress. Do not describe an unseen boss map as proven blocked.
- **Required:** §6.11 phase-specific outcomes; §8.9 reliable phase transitions and retry; terminal events cannot depend on a continuing animation action once gameplay state is committed.
- **Decision:** refactor commit/outcome ownership, retaining target lease and protection code. Capture stable target/phase/instigator identity; once damage/outcome is committed, deliver or persist its exact-once outcome independently of the ability's continuation lease. If cancellation is intended to invalidate the outcome before commit, do not mark the phase resolved until the transaction can fulfill that contract. Handle actor destruction/phase replacement explicitly rather than replaying a stale event into a new phase.
- **Dependencies/risk:** medium-high: boss event graphs, encounter snapshots, cinematic takeover and damage callbacks. Changes must not grant boss kills or allow duplicate outcomes on reload.
- **Order:** after ED-01 and action lifecycle hardening, before boss phase certification.
- **Regression:** aligned phase transaction with cancellation during damage, cinematic takeover, phase mutation and target destruction; save/load both delivered and pending state; exactly one progression outcome and no repeated damage. Current `SovFinisherProjectileRuntimeTests.cpp:30–41` disables navigation and tests fallback/lease/protection reentry; it does not exercise an aligned phase commit at all.

## ED-05: weak-point receipt history is unbounded over a persistent actor's lifetime

**Priority P2, high confidence; memory and long-session reliability.**

- **Exists:** target-owned weak-point proof, 32-entry bounded pending hit list, break state, reset/restore epochs and exact consume-once rewards. Consequence effects own their ability block counts and restore only remaining duration.
- **Failure:** `P/Public/Components/SovWeakPointComponent.h:444` owns `TSet<FGuid> ResolvedHitTransactions`; the entire source contains only `Contains` at `Private/Components/SovWeakPointComponent.cpp:520` and `Add` at542, with no eviction/reset. Every accepted hit on an unbroken zone, including below-break-threshold impacts, inserts an ID. `ClearPendingBreaks` (1106–1110) does not clear or retire this set; checkpoint reset, revive and ability-system replacement retain it. Long-lived training targets, repeated retries on a retained actor, or a deliberately high threshold grow the set without bound. It is small for ordinary short-lived enemies; no measured exhaustion claim is made.
- **Required:** bounded long-session memory under console budgets and explicit transient combat history lifetime.
- **Decision:** extend the existing receipt ledger with an explicit owner epoch/lifetime and bounded retention. Do not blindly drop IDs if old externally delivered receipts remain payable: use fresh authoritative transaction/encounter generations or a bounded ordered history with a stated replay window. Corruption producer already demonstrates a 256-entry history at `SovCorruptionSourceComponent.cpp:114–115`, but retention policy should match weak-point receipt security.
- **Dependencies/risk:** medium-low; repeat hit rewards, reset/load replay rejection and live actors across encounters.
- **Order:** after functional transaction fixes, before endurance/performance gates.
- **Regression:** tens of thousands of subthreshold weak-point hits and repeated restore/revive, constant bound on retained IDs, recent duplicate rejection, old-generation receipt rejection, legitimate new-generation hits accepted. Do not duplicate the TSet implementation in the test; drive real target/source result ownership.

## ED-06: Shield and Poise recovery do not fence death or retired avatar ownership

**Priority P2, high confidence for missing gate; downstream effect depends on retained actor lifetime/content.**

- **Exists:** player Health recharge checks Narrative IsDead (`P/Private/Components/SovHealthRechargeComponent.cpp:523–532`) and listens to death (99–101). Shield and Poise have explicit timers, tag-owned interruption state and checkpoint resets.
- **Failure:** `SovShieldComponent.cpp:1137–1140` and `SovPoiseComponent.cpp:866–869` accept any initialized ASC and authoritative owner; neither checks that ASC->GetAvatarActor()==owner or that Health/death/fatal state permits simulation. Neither component subscribes to death. Pending timers can recharge a retained corpse's Shield, refill Poise and transition Broken→Recovering after death. With a long-lived PlayerState ASC, a component that has not yet ended can also write the newly assigned avatar's attributes unless a higher-level handoff path happens to clear all timers first. This contradicts the tighter producer ownership checks elsewhere.
- **Decision:** extend these components with canonical owner/ASC identity and terminal-state gates, owned timer retirement on death/avatar loss, and deliberate restart on revive/checkpoint restore. Preserve Shield's explicit health-only-hit delay policy and Poise recovery immunity. Consider a common validation helper, not a second attributes owner.
- **Dependencies/risk:** medium: handoff ordering, retry restoration and intended corpse equipment presentation. Do not silently remove other systems' tags/effects; test live respawn as well as retained corpse behavior.
- **Order:** in the lifecycle hardening slice, before end-to-end retry tests.
- **Regression:** lethal damage during pending regen; world timers advance beyond all deadlines while dead; ASC avatar changed without component destruction; legitimate revive then correctly delayed regeneration. Verify no resource/state events from retired owners and no revival by passive regeneration.

## ED-07: drone interruption is not as immediate or callback-safe as Hound/Handler interruption

**Priority P2, high confidence source behavior; severity depends on authored status timing.**

- **Exists:** `SovGameplayAbility_ReformationDrone.cpp:410–440` checks death, Poise break, frozen and device-disabled state before payload work. Hound and Handler also bind tag listeners for immediate cancellation and use activation epochs. The generic drone base does not.
- **Failure:** a finite DeviceDisabled status arriving and expiring between payload callbacks is never observed by the drone ability. A rocket release's `TryBeginWeaponPayloadRelease` checks CanContinue at338, invokes `ReceiveDroneWeaponPayloadReleased` at348, and returns only IsActive at349. A release callback that grants DeviceDisabled without cancelling the ability can return into `LaunchRocket` (1153–1165), which checks only active/finished/attempted and proceeds to spawn at1200–1250 despite the still-present disabling status. The status tag's normal producer may explicitly cancel some actions, but a generic weak-point granted-state consequence only promises that tag and should not depend on every producer hardcoding the enemy class.
- **Decision:** extend the existing drone weapon base with owned immediate interruption listeners, valid end/scope/epoch handling and a final CanContinue/epoch check after Blueprint and spawning boundaries. Reuse the Hound/Handler ownership pattern. Keep the committed self-destruct outward blast alive after source death where its current immutable explosion policy deliberately requires it.
- **Dependencies/risk:** medium-high: burst epoch, rocket manual vs automatic release, self-destruct commit point, montage tasks and native weak-point effects.
- **Order:** action lifecycle hardening slice after ED-01, alongside ED-03.
- **Regression:** short status between timer ticks, DeviceDisabled inside release callback, cancellation/restart from release hook, self-destruct interrupted before commit and source death after commit; no projectile from a cancelled/disabled old action and exactly one allowed committed blast.

The native NPC base creates Dismemberment and SustainDrop by default, while player base creates Shield/Poise and other protagonist systems. Prefer a mandatory archetype validation rule for the components an archetype declares it needs, rather than imposing every subsystem on every NPC or introducing duplicate default components under existing Blueprints.

## Recommended vertical repair sequence for these findings

1. **Combat and resource transactions:** ED-01 and ED-02. Keep damage routing and pickup APIs. Done when nested effects preserve every accepted contribution and one resource pack cannot overgrant; all exact terminal outcomes remain attributable. Run new native GAS/overlap regressions plus affected Echo, weak-point, Guard and death tests.
2. **Action/defense lifecycle symmetry:** ED-03, ED-06, ED-07. Reuse Guard/Hound patterns. Done when cancellation at every external callback leaves no old tag, timer, task, movement, cost or projectile, and revive/avatar replacement restores deliberate behavior. Predicted Deflection requires engine/client validation even though campaign is single player.
3. **Boss durable outcome delivery and endurance:** ED-04 then ED-05. Done when cancellation cannot consume a phase without a recoverable outcome; restore cannot repeat damage/events; persistent actors have bounded histories. Add an aligned phase fixture and endurance case, then package/play the actual boss assets.

No whole-game AAA certification is possible from source inspection and portable policy tests. The immediately actionable engineering standard is: explicit transaction/lease ownership; no post-callback continuation without ownership proof; durable outcome convergence; bounded transient work; source and native regression evidence; then UE5.7 compile/UHT and content integration gates.

# Adversarial campaign, encounter, travel, and world audit

Snapshot: ProjectVelkorran local HEAD 6225c68d50fbea605d7c7dfc8d61d5569805e28f (console-pass tree). Read-only source review. No source mutations or UE runtime execution. TDD authority: August 2026 v2, with CampaignV2ChangeLog exceptions. Source paths below relative to repo unless stated otherwise.

## Executive result

The architecture has substantial real safeguards: authored protagonist identity and journal prerequisites; exact co-action and cinematic receipts; per-protagonist resources/kit; two-stage companion staging; verified origin checkpoints; scoped encounter restore; collision sweeps; explicit Mass identity; cancellation guards; finite watchdogs. Preserve those systems. It is not yet airtight: ordinary asynchronous state combinations can permanently block mission progression. Four high-confidence P1 defects should close before treating the engineering as ready for engine qualification. Additional P2 behavior and performance weaknesses require targeted changes and measurement. Existing native tests are useful, but mostly isolated fixtures rather than actual mission traversal; passing their portable policy companions does not establish end-to-end behavior.

## C01: Async mission travel has no origin recovery transaction (P1, high confidence)

- Existing: `Private/Framework/SovPlayerController.cpp:606–665` validates successor and map package, writes an origin checkpoint and account-scoped Narrative player transfer save, sets Travelling/input lock, invokes ServerTravel. `Private/Framework/SovCampaignGameMode.cpp:45–68` reads destination transfer and validates ownership; controller `:470–471` checks destination identity.
- Required: TDD11.7 validates destination, saves before irreversible travel, preserves campaign state, and recovers to origin checkpoint if load fails; 15.16 explicit recoverable errors.
- Defect: the only travel error branch is synchronous ServerTravel false at `:656–663`. No `TravelFailure`, `NetworkFailure`, or equivalent binding exists in project source/plugin. Once ServerTravel accepts the request, no GameInstance-owned transaction survives source-PC destruction and handles corrupt/missing dependency packages, destination InitNewPlayer rejection, or post-travel initialization failure. A placed PC is not a sufficient lifetime owner. Destination errors return strings, and first-map initialization failure has no origin snapshot (only same-world handoffs capture OriginSnapshot).
- Reproducer: valid/cooked destination package passes DoesPackageExist; ServerTravel returns true; force a destination dependency failure or make its InitialMission/entry readiness incompatible. Verify no native code starts the previously written origin checkpoint. Another case: storage owner becomes unavailable before destination reads transfer and InitNewPlayer rejects.
- Preserve/extend: keep SaveSubsystem and Native travel serializer. Extend existing GameInstance save/transition coordination with one tokenized mission-travel transaction containing origin checkpoint reference, intended mission/map/account generation, deadline, and state. Bind engine failure once. Recover via the existing LoadSlot path, with recursion bounded and explicit recovery UI if origin also fails. Do not create a second save layer.
- Dependencies: save account ownership, lifecycle resume timing, map startup, frontend recovery. Risk high because crossing worlds/account changes; fix before new travel features.
- Regression: accepted travel then injected delayed failure; destination InitNewPlayer failure; initialization timeout; source controller gone; origin load itself fails; signout during each phase; stale failure from a prior transaction cannot restore over a newer run. Assert exactly one recovery attempt, no false mission-start autosave, and no permanent input lock. Needs UE multiworld/packaged functional harness, not just a policy boolean test.

## C02: Final required kill during unrelated Mass promotion loses victory forever (P1, high confidence)

- Existing: `Private/Campaign/SovEncounterDirector.cpp:480–502` records each confirmed kill and invokes CompleteEncounter once all required IDs appear. `:413–415` refuses completion while `MassPromotions` is nonempty. `Private/Campaign/SovEncounterDirectorMass.cpp:589–652` asynchronously waits, restores and releases replacements.
- Required: TDD8.7 encounter completion/recovery,8.4 conversion must preserve mission ownership; no required encounter can remain Active with completed victory conditions.
- Defect: after final promotion succeeds, `Mass.cpp:641–645` removes its pending entry/rebinds deaths but never re-evaluates completed victory conditions. Search confirms CompleteEncounter is only invoked automatically by HandleDeath. No new required death remains to cause another attempt.
- Reproducer: A required hostile, B optional opted-in hostile in the current wave. Demote B then begin its actor promotion with delayed appearance initialization. Kill A while B is pending. All required IDs are recorded but CompleteEncounter returns false. Finish B initialization. Encounter remains Active permanently and blocks mission travel.
- Preserve/extend: centralize an idempotent EvaluateCompletionConditions and a deferred completion latch, called after confirmed death and every mutation/promotion stabilization. Do not simply complete inside the mutation guard since CompleteEncounter currently refuses bMutationInProgress. Execute after releasing the guard and validate attempt/generation. Optional actor's promotion failure must produce one declared failure, not accidental success.
- Dependencies: actor/promotion lifetime, reward/autosave exactly-once. Risk medium; tightly local state-machine repair. Recommended first campaign fix alongside C03.
- Regression: actual director with required A/optional B and controlled delayed B readiness; kill A then resolve B. Assert Succeeded once, Echo reserve normalizes once, exit autosave/reward once. Repeat promotion failure, simultaneous player death, cancellation/retry, and queued stale completion for old AttemptId. Existing `SovCampaignMassRuntimeTests.cpp` tests required-demoted wave blocking and simple roundtrip, not this interleaving.

## C03: Unexpected required participant loss has no failure route; wave gate disagrees with victory gate (P1, high confidence)

- Existing: director binds only GAS OnDeathStateChanged `SovEncounterDirector.cpp:455–502`. It deliberately requires `DefeatedParticipants` rather than counting arbitrary actor destruction. This is correct for rewards. Tick `:820–824` only maintains restore/promotion; no active participant liveness reconciliation.
- Production path: `Plugins/Narrativeed3f9374a6eV6/Source/NarrativeArsenal/Private/UnrealFramework/NarrativeNPCCharacter.cpp:76–92` ordinary multiple-instance NPC FellOutOfWorld calls authored CleanUp(0) or directly Destroy at89 if no controller. Explicit Destroy/streaming EndPlay likewise need not produce a GAS death receipt. CleanUp is BlueprintImplementable, so its exact content behavior cannot be assumed from checkout.
- Defect: removing a required actor without death leaves victory unresolved forever. Worse, `Private/Campaign/SovEncounterCoordinationComponent.cpp:532–551` skips invalid actors at542 and may advance the next wave anyway, while the director still waits for the missing required ID. Mass-backed missing actors correctly retain the wave gate at536–540, but unexpectedly missing ordinary actors do not.
- Required: TDD8.7 participant ownership/wave gates,11.10 no unresolved critical actor unload,15.16 explicit recovery.
- Reproducer: begin a two-wave encounter, destroy one current required NPC without calling Kill/Die, tick coordinator. Future wave can activate; completing all surviving required NPCs never succeeds because lost ID lacks a receipt. Single-wave variant remains Active indefinitely.
- Preserve/extend: keep confirmed-kill ledger. Add actor EndPlay/destruction observation tied to participant identity, attempt, representation generation. Explicit sanctioned loss reasons for demotion/retry/normal corpse cleanup; unexpected loss holds waves and fails/restarts the encounter through existing recovery. Add critical actor residency ownership for streaming. Do not award a kill for disappearance.
- Dependencies: Narrative cleanup, World Partition, Mass demotion, encounter reset and fatal recovery. Risk medium/high due intentional destruction during replacement; generation/reason discrimination essential. Order with C02 before content scale-up.
- Regression: Destroy before death, after recorded death, current/future wave; source destruction during legitimate demotion; proxy/entity loss; streamed-out required actor; retry destruction. Assert neither forged reward nor premature wave, one clear failure, and successful existing checkpoint retry.

## C04: Cinematic startup ignores acknowledged save failure and reopens the same blocker (P1, high confidence; verified with save/platform reviewer)

- Existing: cinematic `Private/Cinematics/SovCampaignCinematicComponent.cpp:484–485` always calls WriteCheckpoint(CanonGate,BeatId). Other transition paths consume exact one-shot save acknowledgements before another write (`SovPlayerController.cpp:234–235`, encounter `:366–367`).
- Defect: WriteCheckpoint itself never consumes the acknowledgement (`Private/Save/SovSaveSubsystem.cpp:510–516`). Continue/acknowledge records an exact receipt via `:745–755`; consumption only via `:734–743`. A full-storage player chooses continue without a fresh checkpoint, retries required cinematic, and encounters the same failed write again. The pre-cinematic path cannot progress under its existing advertised acknowledgement behavior.
- Required: TDD18.9 low-storage handling and11.7/15.16 explicit recoverable transitions; existing product's concrete acknowledgement contract must be honored consistently.
- Preserve/extend: use existing receipt API with exact CanonGate/BeatId, then still enforce epoch, owner, mission, current pawn and playback generation. Prefer one existing SaveSubsystem helper used uniformly by every irreversible action, avoiding divergent call-site semantics.
- Dependencies: save UI, account/lifecycle revocation. Risk low/medium; no schema change. Order immediately with travel recovery.
- Regression: force checkpoint write failure; acknowledge exact beat; next RequestPlay starts once without issuing another write. Wrong beat/world/hero/account, expired receipt, stale receipt after successful save must reject. Assert no Saved feedback for acknowledgement and final post-scene autosave retry remains separate.

- Preserve/refactor: existing Narrative activity and attack candidate API. Derive desired attack position from target and weapon candidate range, use existing path following with a bounded pursuit leash around leader, validate current target/command ID after move callbacks. Restore previous focus when target invalidates; provide failure/ack feedback. Do not bolt on independent companion controller.
- Dependencies: bot attack range contracts, nav, camera/lane avoidance. Risk medium behavior change; stage after progression blockers.
- Regression: real navmesh path for melee/ranged companion, target retreat/moving, obstacle/partial-path refusal, target death, command replacement, leader leash, held position. Assert approach reaches usable range and obeys contribution/player-finish caps.

## Level1/Level2 implications and proposed acceptance route

M01_Mantle and M02_OneDegree native mission constructors define actual beat skeletons (`SovCampaignDefinition.cpp:323–373`), including proof-gated heir/shot/market/extraction scenes and Lyric arrival proof. The repo cannot prove authored map contents, PlayerStart, correct PlayerDefinition/appearance/ability sets, cinematics, nav links, or encounter assignments from source alone. Those are editor/cooked-content dependencies, not evidence of missing C++.

The minimum integration route must drive real APIs and public event paths: new M01 -> ready Tarrik -> first encounter entry write -> loss/retry -> canonical scenes -> market refusal -> completed M01 -> accepted map travel -> M02 Selene with intact separate snapshot -> infiltration/shot/escape -> Lyric nav arrival -> extraction/Voss. Save/reload before/after each canonical boundary. Inject C01/C02/C03/C04 at reachable stages, and reject false success. Existing policy and toy-world tests should remain, supplemented by one multiworld mission fixture and a packaged functional route.

Recommended order: (1) C02/C03 encounter state reconciliation; (2) C04 acknowledgement parity + C01 persistent travel recovery, coordinated with account/lifecycle fixes; (3) C05 companion pursuit and real nav failure tests; (4) C06 residency; (5) C07 animated crowd after content/performance decisions. UHT/UBT and actual existing native suites remain mandatory before approval for playable-engine readiness.

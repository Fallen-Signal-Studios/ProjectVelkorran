## E1. Selene has a command-link transaction but no native pulse release connecting it to combat (P0, recommended first implementation)

- Exists: `USovGameplayAbility_SeleneAxiomNullPulse` costs 30 Echo, is restricted to Axiom, and exposes shield-disruption/suppression/optional-disable effect classes plus charge/range/cone configuration (`P/Private/Abilities/SovGameplayAbility_SeleneEcho.cpp:109–188`, public header :154–206). `TrySeverAxiomCommandLink` validates authority, active ability, target world and maximum distance, calls the existing link component and consumes the verified Echo reward. - TDD: §5.3 Sever costs 30 and breaks links/disables eligible devices/interrupts specialists; §8.11 requires this to change coordination observably. Later `Docs/SeleneCommandLinkAndWeakPointReveal.md:3–5` explicitly makes Axiom the project-specific Sever implementation. Preserve that decision rather than adding a second Disrupt ability.
- Gap: native defaults cannot deliver the complete player action. A Blueprint can call the public helper through walls because the helper only enforces maximum distance; its documented caller contract requires targeting before calling it, so this is an incomplete native contract, not proof current local BP cheats. Shield effect and recharge-block classes are not assigned native defaults.
- Decision: EXTEND Axiom in place; PRESERVE link component, reward consumer and existing Echo spend framework. Native authority charge/release should select hostile targets in the actual cone with collision occlusion, apply shield-only resolved damage and finite suppression, optionally apply eligible device disable, invoke the existing link transaction once per authored network, and end/cancel exactly once.
- Dependencies: Echo ability base and equipment validation; Narrative damage execution (Health coefficient zero, Poise coefficient zero unless deliberately authored); shield regen blocked tag; team interface; command-link component; Selene Echo generator; existing enemy consumers. Avoid treating shield collapse/device status as a successful Sever reward.
- Risk: medium/high because charge input, synchronous GAS cancellation, reward reentrancy and existing Blueprint release logic can double-fire or double-spend. Gate native/manual ownership clearly and migrate local BP hook instructions. Preserve cancelled-before-release behavior intentionally.
- Order: first runnable Selene disruption slice after establishing engine/build availability; before adding more enemy roles or a parallel AI framework.
- Validation / done: unshielded target gets no health or poise loss from shield payload; shielded target collapses appropriately and cannot recharge during finite duration; hostiles outside cone, beyond range, behind wall, friendly actors, dead/immune targets are rejected; active Handler link severs once and charge cancels; repeat pulse on severed link gives no second +12; independent Bite/Pounce survive link Sever; zero/insufficient Echo, equipment swap, death/cancel and hold/release edge cases clean up. Add actual world/GAS tests, not just CDO default assertions. PIE content and full CompileAllBlueprints remain required gates.

## Integration notes for native Axiom DeviceDisabled effect

1. `Sov.State.Status.DeviceDisabled` already has native consumers. Hound all attacks gate at `...DominionHound.cpp:121` and subscribe for immediate cancellation at :1133–1199. Handler blocks at `...DominionHandler.cpp:49`, subscribes :716–786, and CanIssueHoundCommands checks :156–158 in its character file. Drones block activation :110; re-check before payload :405–435, during pursuit :1504–1515 and immediately before detonation :1765 in ReformationDrone.cpp.
2. Link Sever must keep Bite/Pounce available. Applying DeviceDisabled indiscriminately to every link participant would cancel all three Hound attacks and violate that contract. Axiom may sever a Handler link while applying device disable only to explicitly eligible mechanical actors, such as project drone base/type or authored opt-in tag. Do not infer device eligibility from generic ASC existence.
3. Status immunity requires explicit application qualification; a loose tag named immunity does nothing by itself. CommandLink already checks `Status_Immunity_DeviceDisable` on owner/source (:440–462). Direct status application must additionally respect it. Damage immunity and status immunity are different contracts.
4. Prefer finite duration GE granting the status tag (owned/tag-count semantics) and remove only own active effect handle. Never manually clear other system contributions. Determine reapplication policy so a short pulse cannot accidentally shorten an existing longer disable.
5. Drone interruption is polled, so very short status duration can be missed between shot/pursuit callbacks; authored durations should exceed the interval, or extend drone immediate tag listeners if reliable short interruptions are in scope. Hound/Handler cancellation is already synchronous.
